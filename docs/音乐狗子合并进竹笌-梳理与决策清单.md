## d. 离线 outbox 重合情况

| 能力 | 副 App `LocalChatRepository`(198) | 主 App `ChatLocalDataSource` + `SyncEngine` |
|---|---|---|
| 数据库 | `zhuyapp_chat.db` | 同一套 sqflite（独立 db 文件） |
| 表 | `chat_history` + `outbox` | `chat_history` + `outbox`（字段更多） |
| 乐观写 | `appendUserMessage` | `appendUserMessage` |
| 标记 | `markSynced` / `markError` | `markUserSynced` / `markOutboxSynced` / `incrementAttempt` |
| 重发 | `flushOutbox(chatFn)`，**遇首个失败即 break** | SyncEngine `_resend()`，**指数退避 1s→2s→4s…上限 30s** |
| 触发时机 | 页面 `initState` 手动 `_tryFlush()` | 联网恢复监听 + 启动即 flush + **30s 定时兜底** |
| 上下文 | 无（只发单条） | `getHistoryBefore(clientMsgId)` 带真实历史上下文 |
| 通知 | `syncStream` | `syncStream`（`chat_provider` 已监听并自动刷新消息列表） |
| attempts / 错误信息 | 无 | `attempts`、`last_error` 字段 |

**结论**：主 App 是**严格超集**（多退避、多 attempts、多上下文、多定时兜底、已与 Riverpod 打通）。副 App 版本搬进来会产生第二个 db 文件、第二套表结构、第二套同步入口，且功能更弱。

消息实体重复度：**3 份**（主 `domain/entities/message.dart` + 主 legacy `providers/...Message` + 副 `data/message.dart`）。

## e. 待拍板的冲突与决策项

### 决策 1 — 音频库：just_audio vs audioplayers

现状：主 App **只有 just_audio**（用在 3 个 TTS 服务：cartesia / minimax / tts_service），**lock 中无 audioplayers**；副 App audioplayers 出现在 2 个文件（`pet_studio_page` 的 `_MusicPlayer`、`tts_service`）。

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 统一 just_audio**（默认倾向，由你定） | 不新增依赖；把 `_MusicPlayer` 的 `AudioPlayer.play(UrlSource)` 改为主 App 既有播放方式；副 App tts_service 整体不搬 | 需改副 App 约 20–30 行播放代码；两者 API 不同（`onDurationChanged`→`durationStream`、`play(UrlSource)`→`setUrl`）；优点：单一音频引擎、无焦点冲突 |
| **B 新增 audioplayers，副 App 原样搬** | pubspec 加一条依赖 | 两套音频引擎并存，二进制体积变大；Android 端音频焦点/后台播放模式可能互相打架；优点：副 App 代码零改动、落地最快 |
| **C 分工共存** | TTS 继续 just_audio，音乐播放用 audioplayers | 实际上就是"原样搬"的自然结果；长期维护两套心智模型 |

### 决策 2 — 宠物模块：替换 / 并存 / 混合

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 替换 `/pet`** | 用副 App 创作台 + DogPainter 覆盖主 App PetPage | 主 App 现有 830 行（pet_page 708 + pet_fullscreen 122）被弃或重写；副 App 是奶油橙棕配色（硬编码 `Color(0xFFFAF4EF)`/`Colors.orange`/`brown.shade700`），与竹笌 `AppTheme`（竹绿/竹炭/暖阳）视觉冲突，必须重新皮肤化；`/pet/full` 是否保留要定 |
| **B 新增路由并存** | 加 `/pet/studio` 之类，与现有 `/pet` 并存 | 零删除风险、两套都能跑；代价：代码重复、两套宠物状态字段、用户路径分叉、维护两份宠物逻辑 |
| **C 混合**（拆最细） | 只搬 `DogPainter`+`DogBarkLibrary`+`SpeechBubble`+`LoveMeterBar`（形象层）与创作台流程，保留主 App `/pet/library`、`/pet/full`、`AppTheme` 皮肤 | 需要把副 App 硬编码配色替换成 `AppTheme` 变量，改动面中等；形象与流程都能复用 |

**子问题：副 App 三 Tab 首页（HomePage）是否保留？** 三个 Tab 全部为 `static const` 硬编码（`_songs` / `_recommendSongs` / `_stats`），无联网、无业务，`_QuickAction` 无 `onTap`，唯一交互是 push 到 PetStudioPage。可选：**不搬**（推荐理由：主 App 已有 `/discover`、`/profile` 两个同级页面，重复度最高、价值最低）／**搬成独立路由整体保留**／**只搬其中的歌曲卡与风格 chip 组件**。

### 决策 3 — 状态管理：setState 原样 vs Riverpod 重写

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 原样保留 setState，仅挂 go_router 路由** | 2185 行几乎零改动，只把 `Navigator.push(MaterialPageRoute)` 换成路由跳转 | 落地最快；代价：与主 App Riverpod 风格割裂；宠物状态无法与 `chatNotifier`/`affinityProvider` 联动；主题不跟随 `AppTheme`（副 App 硬编码奶油色，暗色模式下会割裂）；`context.pop()` 与 Navigator 混用需小心 |
| **B 重写为 Riverpod**（`StateNotifierProvider` / `AsyncNotifier`） | 状态与数据获取全部 Provider 化 | 一致性最好、可复用 `BackendService`、主题统一、可与聊天状态联动；代价：2185 行重构，`TickerProviderStateMixin` 迁到 `ConsumerStatefulWidget` 时动画控制器生命周期要重处理，工作量最大 |
| **C 折中** | 页面仍 `StatefulWidget`，只把"宠物状态获取"和"播放状态"抽成 Provider（如 `petStateProvider` / `musicPlayerProvider`） | 改动可控；UI 仍局部 setState，但数据入口统一到 BackendService，主题可跟随 |

### 决策 4 — 额外发现的 6 个必须一起拍板的项（不决定会卡住）

1. **宠物状态字段体系二选一**：主 `energy/bond/hunger/happiness/level/exp` vs 副 `love/total_barks/songs_created`。**涉及后端**，前后端需同一次定。
2. **后端端点路径二选一**：`/generate` vs `/music/generate`；`/pet/state` 是否保留 `{userId}` 路径参数（主 App 无 userId 概念，靠 HMAC 签名识别用户）。
3. **是否引入 `flutter_animate`**：副 App 3 个文件（main / chatty_dog_pet / pet_studio_page）大量使用，主 App lock 中**没有**。要么新增依赖，要么剥离所有 `.animate()` 链式调用（剥离量不小，`pet_studio_page` 与 `chatty_dog_pet` 里到处都是）。
4. **宠物形象走 2D 还是 3D**：主 App 已有 `assets/vrm_test/dog_avatar.glb` + `VrmAvatarView`（3D），副 App 是 `DogPainter` 手绘 2D。二者是替代还是分场景（聊天页 3D / 宠物页 2D）。
5. **创作台的对话走哪个后端**：副 App 用 `/chat`（同步 JSON），主 App 是 `/chat/v2`（SSE 流式）→ 是否统一到流式（决定创作台能否与 `ChatNotifier` 复用）。
6. **音乐播放器"历史"Tab 的空壳**：主 App `/pet/library` 的历史 Tab 是占位，`generateMusic()`/`getMusicJob()` 无调用点——副 App 的创作台正好能接上这一段，但"历史"到底展示什么（生成任务记录？已生成歌曲？）需你定义。
