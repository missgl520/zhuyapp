## 2. 执行中发现的关键事实校正

执行中实测后端契约，纠正了计划里两处「想当然」假设：

1. **后端没有 AI 自动生成歌词能力。**
   `routers/lyrics.py` 的 `POST /lyrics` 要求 client 自带 `title` + `content`（纯 CRUD，缺一则 400）。副 App 原 `PetApiService.createLyrics(theme, style, mood)` 返回 AI 生成歌词文本的契约**不存在**。
   → 适配：狗子对话走 `/chat/v2` SSE 拿回复文本，把回复当 `content` 存入歌词；歌词「创作」不再依赖服务端 AI。

2. **音乐生成是异步任务，需轮询。**
   `POST /music/generate` 返回 `job_id`（body 带 `prompt/lyrics_id/style/title/duration`）；`GET /music/jobs/{id}` 返回 `status`(pending/running/done/failed) + `audio_url` + `duration`。`audio_url` 是**相对路径**（`/music/audio/{job_id}.wav`），需拼 `BackendConfig.baseUrl` 才能 just_audio 播放。

3. **主 App 宠物状态是 `Map<String,dynamic>`，无 `ZhuyPetState` 类。**
   计划假设的 `ZhuyPetState.fromBackend` 在主 App 不存在，需新建。

4. **分支拓扑有混淆。** 本地 `main` 跟踪 `origin/zhuyu`；GitHub 的 main 实际是 `zhuyu` 分支。PR base 选 `zhuyu`。

## 4. 新的数据流（音乐狗子对话 → 歌词 → 音乐）

```
用户输入 "帮我写首失恋的歌"
   │
   ▼ askDog() → BackendService.streamChat(/chat/v2 SSE) 流式累积回复
   │
   ▼ 启发式意图识别（命中「歌词」）→ _createLyrics()
   │     BackendService.createLyrics(title=主题, content=狗子回复, mood, tags=[风格])
   │     → 存 _lastLyrics(LyricsResult, 含 id)
   │     → 顶部 _LyricsPreview 展示
   │
   ▼ 若命中「音乐」且无 _lastLyrics → _generateMusic()
   │     BackendService.generateMusic(prompt, lyricsId, style, title) → job_id
   │     轮询 BackendService.getMusicJob(job_id)（每 2s，最多 30 次）
   │     done → audio_url 拼 BaseUrl → _MusicPlayer(Slider 拖动 seek)
```

> 说明：副 App 原始「AI 自动产出歌词文本」在现有后端不存在，故用狗子 SSE 回复作为歌词 `content`，保证端到端流程可跑、可落库、可生成。
